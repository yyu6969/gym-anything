A task is one specific thing the agent is asked to do inside an environment.

In Moodle, a task might ask the agent to enroll a student in a course.

In some other environment, a task might ask it to configure a setting, export a file, fill in a form, or fix something that's broken.

So a task isn't the whole environment. It's one job inside that environment.

## What Makes A Task Different From A Prompt

<Callout type="info">
A task here is more than just an instruction string. It includes setup code, export logic, and an automatic checker — that's what makes it reusable and testable.
</Callout>

It usually comes with:

- a written goal
- code that prepares the right starting state
- code that exports the result at the end
- code that checks whether the task was solved

## One Real Task Folder

Here is a real task folder from the Moodle benchmark:

```text
benchmarks/cua_world/environments/moodle_env/tasks/enroll_student/
  task.json
  setup_task.sh
  export_result.sh
  verifier.py
  README.md
```

The files mean:

- `task.json`: the task description and settings
- `setup_task.sh`: prepares the exact starting state
- `export_result.sh`: saves task-specific results at the end
- `verifier.py`: checks whether the task passed
- `README.md`: optional human explanation

## What `task.json` Usually Contains

`task.json` is the main file to read first.

In a typical task, it tells you:

- the instruction shown to the agent
- the timeout and step limit
- which setup script runs before the task
- which check runs at the end

A simplified example looks like this:

```json
{
  "description": "Enroll the student 'Jane Doe' in the 'Intro to Biology' course.",
  "init": {
    "timeout_sec": 300,
    "max_steps": 40
  },
  "hooks": {
    "pre_task": "/workspace/tasks/enroll_student/setup_task.sh",
    "post_task": "/workspace/tasks/enroll_student/export_result.sh"
  },
  "success": {
    "mode": "program",
    "spec": {
      "program": "verifier.py::verify_enroll_student"
    }
  }
}
```

## What Happens When The Task Runs

The normal flow is:

1. the environment starts
2. the task setup script runs
3. the agent receives the task instruction
4. the agent interacts with the software
5. the run is finished with `mark_done=True`
6. the task export and final check run

If you're driving the environment directly from Python, the finish step usually looks like this:

```python
obs, reward, done, info = env.step([], mark_done=True)
```

That's the step that tells Gym Anything to end the task cleanly and run the final task logic.

## What The Setup Script Is For

The setup script makes the starting point specific to that task.

For the Moodle `enroll_student` task, the setup script:

- resets the Moodle database state
- creates the student and course records
- restarts the Moodle service
- leaves the app ready for the agent to begin

Without that step, the task wouldn't start from a known state.

## What The Final Check Is For

The final check decides whether the task succeeded.

Most of our benchmark tasks use a Python check in `verifier.py`. That check can look at things like:

- files created during the run
- exported JSON or CSV output
- application state
- database contents
- screenshots from the run

For the Moodle enroll-student task, the checker queries the Moodle database and verifies that the correct student was enrolled in the expected course.

We also support image-based checks, mixed checks, and VLM checklist checks, but most tasks use code in `verifier.py`.

VLM checklist tasks use a checked-in `vlm_checklist.json` file in the task folder. The verifier reads the checklist, samples screenshots from the trajectory, asks the configured VLM to score each checklist item, and returns the normal verifier shape with `passed`, `score`, and `feedback`.

```json
{
  "success": {
    "mode": "vlm_checklist",
    "spec": {
      "checklist": "vlm_checklist.json",
      "model": "gemini-3-flash-preview",
      "completion_threshold": 80,
      "integrity_threshold": 0.75
    }
  }
}
```

Checklist generation is intentionally separate from task execution. Normal evals assume the checklist already exists.

### Post-hoc reference evidence policy

`gym_anything.verification.vlm_checklist.evaluate_reference_checklist` is an asynchronous, opt-in API for fixed reference criteria and an explicit evidence manifest. Select `scoring_policy: "reference_evidence"`; each item supplies `id`, `criterion`, and `evidence_scope` (`terminal`, `trajectory`, or `auxiliary`). Manifest records supply unique IDs, availability, scope, and image paths or selected state values. An optional query callback can supply an existing application's model transport; otherwise the API uses `query_vlm`.

Results distinguish PASS (1), FAIL (0), UNOBSERVABLE (null), and ERROR (null), with reasoning and validated evidence references. Missing evidence is unobservable; malformed, incomplete, duplicate, or out-of-scope judgments are errors. Terminal criteria cannot cite earlier trajectory frames. Callers own evidence loading and provenance, interpretation of references, and Boolean group aggregation. This API performs no environment lifecycle or artifact discovery. Existing task-completion/integrity and external binary outcome policies retain their grading behavior.

## External binary outcome checklists and Harbor export

The Harbor compiler accepts `instruction`, `verifier_bundle`, and `packaging_mode` keyword arguments. A bundle directory contains an authoritative `checklist.json` and arbitrary provenance assets. It is packaged under `environment/verifier/`; both Docker and the custom Gym backend resolve the same file outside the agent-controlled guest. A missing or altered bundle fails closed rather than using the task's program verifier or canonical checklist.

A checklist with `schema_version: "binary_outcome_checklist"` contains `items` with unique `id`, outcome text (`criterion`, optional `description` and `condition`), and `scoring: "binary"`. Its `scoring_policy` is an opaque producer identifier. Each verdict must be exactly `PASS` or `FAIL`; missing, duplicate, invalid, or incomplete verdicts earn zero. All items are equal, points and weights are rejected, score is the percentage passed, and success/reward require every item to pass. Existing task-completion/integrity checklists retain their current grading behavior.

Explicit `packaging_mode="registry_ref"` requires `gym_anything_ref` to be a full immutable commit SHA shared by Gym and CUA-World. Omitting the packaging mode retains the historical thin artifact and ref defaults. `packaging_mode="vendored_snapshot"` packages shared environment assets, the selected task, and the compiler's current Gym runtime. Digests record deployment content; runtime loading bypasses the registry, resolves mount paths inside the snapshot, and writes recordings outside it. Snapshot inputs require environment-local mount sources and reject external symlinks. Presets remain part of the packaged Gym runtime. Runtime dependency and base-image provisioning still follow the normal Gym execution requirements.

## If You Want To Understand A Task Quickly

Read these files in order:

1. `task.json`
2. `setup_task.sh`
3. `verifier.py`

That gives you the shortest path to understanding:

- what the agent is supposed to do
- what the task changes before the agent starts
- what the checker will accept as success

## If You Want To Create A New Task

The simplest workflow is:

1. copy an existing task folder that's close to what you want
2. change the instruction in `task.json`
3. update the setup script so the starting state matches the new goal
4. update the final check so it matches the new goal
5. run the task once yourself and make sure the check behaves the way you expect
